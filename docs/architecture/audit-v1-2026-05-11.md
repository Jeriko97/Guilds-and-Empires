## 1. Résumé exécutif

### Verdict global : PROTOTYPE PRE-ALPHA — FONDATIONS À POSER

Le projet Guilds & Empires n'est pas encore un jeu. C'est un **spike technique Firebase/Auth** de ~250 lignes de code utile. Il n'existe aucun système gameplay, aucune économie, aucune mécanique MMO. C'est un constat neutre : la bonne nouvelle est qu'il n'y a pas de mauvaise dette à rembourser — seulement des fondations à construire correctement.

## 3. Analyse de l'architecture Unity

### 3.1 Ce qui manque (le plus important)

**Aucune architecture de jeu n'existe.** Le projet n'a pas :
- De GameManager / AppController
- De système de scènes / navigation
- De ServiceLocator ou DI container
- De EventBus / MessageBroker
- De SaveSystem
- De StateMachine (app states, game states)
- De ScriptableObjects pour les données de jeu
- D'Addressables pour le chargement d'assets
- De layer d'abstraction entre UI et logique

### 3.2 Problèmes dans le code existant

#### `ProfileService.cs` — Static class avec état implicite
```csharp
// PROBLÈME : FirebaseFirestore.DefaultInstance est appelé à chaque property access
private static CollectionReference Profiles =>
    FirebaseFirestore.DefaultInstance.Collection("profiles");
```
- `DefaultInstance` peut lancer une exception si Firebase n'est pas initialisé
- Pas de vérification d'initialisation
- Aucune gestion du cas "Firebase non disponible" (offline, init failure)

#### `ProfileService.cs` — Listener sans thread marshaling
```csharp
return doc.Listen(snapshot =>
{
    // Ce callback arrive sur un thread Firebase, pas le main thread Unity
    // Appeler statsText.text ici crashe sur mobile
    onChanged?.Invoke(profile);
});
```
**Problème critique :** Les callbacks Firestore arrivent sur des threads background. En Unity, toute modification d'UI ou d'objets Unity doit se faire sur le main thread. Ce code va produire des exceptions `[...]can only be called from the main thread` sur certaines versions Unity/Firebase.

#### `AuthUIController.cs` — async void dans les listeners
```csharp
signInButton.onClick.AddListener(async () => await SignInAsync());
```
`async void` dans les lambda Unity est techniquement correct ici (le listener lui-même est `void`), mais les exceptions non catchées dans ces lambdas sont silencieuses. Acceptable mais à documenter.

#### `ProfileUIController.cs` — Race condition auth/listener
```csharp
void OnEnable()
{
    FirebaseAuth.DefaultInstance.StateChanged += OnAuthStateChanged;
    SetupForUser(FirebaseAuth.DefaultInstance.CurrentUser); // appelé avant que Firebase soit initialisé?
}
```
Si Firebase n'est pas encore initialisé quand `OnEnable` est appelé (scène chargée trop tôt), `DefaultInstance` throw. Pas de guard.

### 3.3 Orientation — ERREUR CRITIQUE DE CONFIGURATION
```
Default Screen Orientation: LandscapeLeft (4)
```
**Pour un MMO mobile avec sessions 15-30 min, Landscape est correct.** Mais il faut vérifier que c'est intentionnel vs la valeur par défaut. Si le jeu est portrait (comme la majorité des MMO mobiles idle/économiques), c'est une erreur.

### 3.4 Company Name non configuré
```
Company Name: DefaultCompany
```
**À corriger avant tout build release.** Impacte le bundle ID, les stores, les certificats.

## 4. Analyse de l'architecture Firebase

### 4.1 Sécurité Firestore — CRITIQUE

**Il n'existe aucune Security Rule visible dans le projet.** Par défaut, Firestore en mode test permet à n'importe qui de lire/écrire n'importe quel document.

Le code actuel dans `ProfileService.AddGoldAsync` :
```csharp
// N'IMPORTE QUEL CLIENT peut appeler cette fonction avec n'importe quel uid
public static Task AddGoldAsync(string uid, int amount)
{
    // amount peut être négatif, 999999, ou tout autre valeur
    // uid peut être celui d'un autre joueur
```

**Sans Security Rules, n'importe quel joueur peut :**
- Modifier le gold de n'importe quel autre joueur
- Passer `amount = 1000000`
- Lire tous les profils de tous les joueurs
- Supprimer des documents

### 4.2 Schéma Firestore actuel

```
profiles/
  {uid}/
    level: int
    gold: int
    displayName: string
    uid: string (REDONDANT — le document ID est déjà le uid)
```

**Problèmes :**
- `uid` stocké en double (dans le document ET comme document ID)
- Aucun `createdAt` / `updatedAt` timestamp
- Aucun champ de validation (version schema, etc.)
- Flat document — impossible d'évoluer vers guildes, inventaire, etc.

### 4.3 Authentification

Email/password uniquement. Pour un MMO mobile F2P :
- Pas de Google Sign-In (Android — essentiel)
- Pas d'Apple Sign-In (iOS — obligatoire si login social présent)
- Pas d'Anonymous Auth (onboarding frictionless — critique F2P)
- Firebase App Check installé mais **non configuré** (Play Integrity / DeviceCheck)

### 4.4 Architecture cloud

**Aucune Cloud Function.** Tout ce qui existe est du client-side Firestore direct. Pour un MMO économique, c'est architecturalement incorrect — toute la logique économique doit vivre côté serveur.

## 5. Analyse des patterns utilisés

### 5.1 Service statique (ProfileService)

**Pattern utilisé :** Static utility class  
**Problèmes :**
- Non testable (impossible de mocker)
- Couplage fort à Firebase SDK
- Pas d'injection de dépendances possible
- Difficile à étendre (pas d'interface)

**Pattern recommandé :** Interface + implémentation injectable
```csharp
public interface IProfileService
{
    IDisposable Observe(string uid, Action<Profile> onChanged);
    Task AddGoldAsync(string uid, int amount);
}
```

### 5.2 MonoBehaviour UI Controllers

**Pattern utilisé :** Controllers directement sur les GameObjects  
**Problèmes :**
- Pas de séparation View/ViewModel
- Logique métier dans les controllers UI
- Pas de data binding

**Pattern recommandé :** MVP ou MVVM simple (sans framework lourd)

### 5.3 Async/Await

Correct pour Firebase SDK. Mais absence de `CancellationToken` partout — les opérations continuent après que le GameObject est détruit.

### 5.4 Listener pattern (IDisposable)

`ProfileUIController` gère correctement le cycle de vie du listener Firestore dans `OnEnable/OnDisable`. C'est **le meilleur pattern existant** dans le projet — à généraliser.

## 7. Problèmes mobiles critiques

### 7.1 Gestion offline

Firebase Firestore supporte le cache offline mais **il n'est pas configuré** :
```csharp
// À ajouter à l'init Firebase
FirebaseFirestore.DefaultInstance.Settings = new FirebaseFirestoreSettings
{
    PersistenceEnabled = true, // cache local
    CacheSizeBytes = FirebaseFirestoreSettings.CacheSizeUnlimited
};
```
Sans ça, une perte de réseau = app cassée. Sur Android mid-range avec connexion instable, c'est fréquent.

### 7.2 Thread safety

**Problème documenté avec Firebase Unity SDK :** les callbacks Firestore/Auth ne sont pas garantis sur le main thread Unity. Il faut un dispatcher :
```csharp
// Pattern nécessaire dans tous les callbacks Firebase
UnityMainThreadDispatcher.Instance.Enqueue(() => {
    onChanged?.Invoke(profile);
});
```

### 7.3 Initialisation Firebase

Firebase SDK Unity v13.x peut prendre 2-5 secondes à s'initialiser sur des appareils lents. Sans loading screen et guard, l'app crashe ou affiche une UI cassée.

### 7.4 Taille du build

Firebase SDK (Auth + Firestore) ajoute environ **15-25 MB** au build Android. Avec les autres packages actuels (Visual Scripting, 2D animation non utilisée), le build sera lourd. Les stores recommandent < 100 MB pour l'APK initial.

### 7.5 Orientation écran

L'orientation `LandscapeLeft` est configurée mais aucune Safe Area n'est gérée dans le code (encoches, barre de navigation Android). Pour mobile, `Screen.safeArea` doit être appliqué.

### 7.6 Consommation batterie

Firestore real-time listener actif en permanence = connexion WebSocket ouverte = drain batterie sur mobile. Il faut une stratégie de suspension (app en background → fermer les listeners).

## 8. Sécurité & anti-triche

### 8.1 État actuel : AUCUNE PROTECTION

La surface d'attaque actuelle est totale :

**Vecteurs d'attaque disponibles AUJOURD'HUI :**

1. **Gold injection directe** — N'importe quel client peut appeler `AddGoldAsync(anyUid, 999999)` via un client modifié. Il n'y a aucune validation côté serveur.

2. **Profile hijacking** — Sans Security Rules, un joueur peut écrire dans le document Firestore d'un autre joueur.

3. **API scraping** — Sans App Check, n'importe qui peut appeler votre API Firebase depuis un script externe avec vos credentials Firebase (qui sont dans google-services.json, distribué dans l'APK).

4. **Memory editing** — Toute valeur économique calculée côté client peut être modifiée avec Cheat Engine ou GameGuardian (Android root).

5. **Replay attacks** — Pas de nonce, pas de timestamp validation.

### 8.2 Security Rules minimales requises

```javascript
// firestore.rules — MINIMUM REQUIS
rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {
    match /profiles/{uid} {
      // Lecture : uniquement son propre profil
      allow read: if request.auth != null && request.auth.uid == uid;
      // Écriture directe client : INTERDITE (passe par Cloud Functions)
      allow write: if false;
    }
  }
}
```

### 8.3 Architecture anti-triche pour économie MMO

Pour un MMO économique, la règle est absolue : **le client ne fait que demander, le serveur décide**.

```
Client                    Cloud Function              Firestore
  |                            |                          |
  |-- requestAddGold(10) ----> |                          |
  |                            |-- vérifier rate limit    |
  |                            |-- vérifier source légale |
  |                            |-- calculer montant réel  |
  |                            |-- écrire atomiquement -> |
  |<-- résultat confirmé ------|                          |
```

**Ce qui doit TOUJOURS être côté serveur :**
- Toute mutation d'état économique (gold, ressources, stock)
- Validation des transactions marchandes
- Calcul des revenus de production
- Validation des achats IAP (receipt validation)
- Anti-farming (rate limiting par joueur)
- Détection d'anomalies (gold/heure anormalement élevé)

### 8.4 Firebase App Check

App Check (déjà installé mais non configuré) permet de vérifier que les requêtes viennent bien de votre app officielle via Play Integrity (Android) et DeviceCheck (iOS). **À activer en priorité.**

## 9. Risques économie server-authoritative

### 9.1 Le problème fondamental

Dans un MMO économique, la logique suivante est catastrophique :
```csharp
// DANGEREUX — logique économique côté client
p.gold += amount; // le client décide du montant
tr.Set(doc, p);   // et l'écrit directement en DB
```

### 9.2 Atomicité et cohérence

Pour un marché MMO, vous aurez besoin de transactions multi-documents :
- Acheteur perd X gold
- Vendeur gagne X gold (moins commission)
- Quantité du stock diminue
- Historique de transaction enregistré

Firestore supporte les transactions multi-documents, mais **avec des limites** :
- Max 500 documents par transaction
- Contention sur documents chauds (prix de marché global = bottleneck)
- Pas de rollback automatique sur erreur réseau

### 9.3 Problèmes d'économie distribuée

| Risque | Description | Solution |
|--------|-------------|---------|
| Double spend | Joueur dépense le même gold deux fois (lag + retry) | Idempotency keys |
| Race condition marchée | Deux acheteurs sur le même item | Transaction + optimistic locking |
| Inflation | Trop de sources de gold sans sink | Design économique + monitoring |
| Gold farming | Scripts automatisés | Rate limiting Cloud Functions |
| Negative gold | Bug de calcul | Validation serveur min(gold, 0) |

### 9.4 Monnaie virtuelle et IAP

Pour la F2P éthique :
- Receipt validation **obligatoire** côté serveur (Cloud Functions)
- Le client ne s'accorde jamais de gemmes/premium currency lui-même
- Apple/Google peuvent rejeter une app sans validation serveur

## 10. Scalabilité MMO

### 10.1 Firestore et le modèle de données MMO

Firestore facture par lecture/écriture/suppression. Pour un MMO avec marché actif :

**Scénario 1000 joueurs actifs simultanés :**
- Si chaque joueur a un listener temps réel sur son profil : 1000 connexions WebSocket
- Si le marché global est un seul document avec listener : **chaque mise à jour = 1000 lectures facturées**
- Coût estimé : $0.06 / 100k lectures → acceptable en early stage

**Scénario 100k joueurs actifs :**
- Un marché global en temps réel = 100k lectures par update de prix
- À $0.06/100k, si les prix changent 10x/minute : $0.06 × 10 × 60 × 24 = **$86/jour juste pour les prix**
- Le modèle Firestore direct ne scale pas pour le marché global

### 10.2 Points de contention Firestore

| Document | Writes/sec max Firestore | Problème si > |
|----------|--------------------------|---------------|
| Profil joueur | 1 write/sec/document | Pas de pb joueur individuel |
| Stock global marchandise | 1 write/sec/document | Marché actif = bottleneck |
| Classement global | 1 write/sec/document | Leaderboard en temps réel impossible |
| Chat global | 1 write/sec/document | Impossible |

**Solution :** Sharding, agrégation via Cloud Functions, ou BigQuery pour les classements.

### 10.3 Architecture recommandée pour scale

```
Firestore (state persistant par joueur)
    + Cloud Functions (logique économique)
    + Realtime Database (présence joueurs, prix en temps réel)
    + BigQuery (analytics, anti-cheat)
```

## 11. Coûts Firebase & synchronisation

### 11.1 Estimation des coûts Firebase (free tier Spark vs Blaze)

**Plan Spark (gratuit) :**
- Firestore : 1 GB stockage, 50k lectures/jour, 20k écritures/jour, 20k suppressions/jour
- Auth : Illimité (email/password)
- Functions : 125k invocations/mois

**Seuil où le plan Spark devient insuffisant :**
- ~1000 joueurs actifs/jour avec usage normal

**Estimation coûts Blaze pour 10k DAU (Daily Active Users) :**
| Service | Usage estimé | Coût mensuel estimé |
|---------|-------------|---------------------|
| Firestore lectures | ~50M/mois | $30 |
| Firestore écritures | ~10M/mois | $18 |
| Cloud Functions | ~5M invocations | $2 |
| Auth | 10k users | $0 |
| **Total estimé** | | **~$50/mois** |

**Risques de coûts non maîtrisés :**
- Listener temps réel mal géré = lectures infinies
- Boucle de retry infinie sur erreur réseau
- Pas d'alertes budgétaires configurées sur Firebase Console

**Action immédiate :** Configurer une alerte budget sur Firebase Console à $10/mois.

### 11.2 Risques de synchronisation client/serveur

| Scénario | Risque | Mitigation |
|----------|--------|-----------|
| Perte réseau pendant transaction | Gold perdu ou doublé | Idempotency keys + retry logic |
| Reconnexion après longue absence | État client obsolète | Toujours fetch depuis serveur au résume |
| Listener Firestore interrompu | Données stales affichées | Heartbeat + reconnection handler |
| Clock skew client/serveur | Tricherie sur timers de production | `FieldValue.serverTimestamp()` obligatoire |
| Cache offline désynchronisé | Joueur voit vieux état | Conflict resolution strategy |

## 12. Risques LiveOps

### 12.1 Remote Config — non intégré

Sans Remote Config, vous ne pouvez pas :
- Modifier les taux de production sans update store
- Lancer un événement temporaire
- Ajuster les prix en temps réel
- Activer/désactiver des features en production
- Faire de l'A/B testing

**Criticité : HAUTE** pour un F2P. Le premier LiveOps event doit pouvoir sortir sans passer par les stores.

### 12.2 Analytics — non intégré

Sans Analytics, vous êtes aveugle sur :
- Funnel d'onboarding (où les joueurs quittent)
- Rétention J1/J7/J30
- Quelles features sont utilisées
- Balance économique (qui a trop de gold, qui en manque)

**Pour un F2P, Analytics est aussi critique que le code gameplay.**

### 12.3 Déploiement Cloud Functions

Sans pipeline de déploiement défini pour les Cloud Functions, chaque modification de logique serveur est manuelle et risquée. Il faut :
- `firebase.json` configuré
- GitHub Actions workflow pour `firebase deploy --only functions`
- Environnements dev/staging/prod séparés

### 12.4 Versioning de schéma

Quand vous ajouterez des champs au profil (inventaire, guildes, etc.), les anciens documents Firestore n'auront pas ces champs. Sans migration strategy, le code plantera sur les vieux documents.

// DÉPLOYER IMMÉDIATEMENT dans Firebase Console → Firestore → Rules

rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {
    
    // Profils : lecture/écriture uniquement par le propriétaire
    // Mais pas d'écriture directe — passe par Cloud Functions
    match /players/{uid} {
      allow read: if request.auth != null && request.auth.uid == uid;
      allow write: if false; // Cloud Functions only
      
      match /{subcollection}/{docId} {
        allow read: if request.auth != null && request.auth.uid == uid;
        allow write: if false;
      }
    }
    
    // Guildes : lecture si membre, écriture interdite (CF only)
    match /guilds/{guildId} {
      allow read: if request.auth != null;
      allow write: if false;
    }
    
    // Marché : lecture publique, écriture CF only
    match /market/{region}/listings/{listingId} {
      allow read: if request.auth != null;
      allow write: if false;
    }
    
    // Tout le reste : interdit
    match /{document=**} {
      allow read, write: if false;
    }
  }
}
