## 3. Méthode de travail (constatée)

**Organisation à trois IA + founder :**
- **claude.ai** = auditeur stratégique et rédacteur de tickets (`BRIEFING-claude-ai.md`).
- **Claude Code** = exécutant (`BRIEFING-claude-code.md`).
- **GPT** = contre-audit.
- **Founder** = décisions design/scope, validation à chaque étape.

**Rituels :** ÉTAPES numérotées (8 → 17.B, sous-étapes 17.A-1…), audit visible avant exécution, tests verts avant commit, commits atomiques conventionnels, `technical-debt.md` (TD-001…015), `phase-1-decisions-log.md` (D-ETAPExx), un log de session par étape, deux briefings resynchronisés à chaque clôture, mémoire Claude Code.

**Forces :** traçabilité exceptionnelle, qualité backend élevée, doctrines claires, décisions motivées avec trigger de revue.

**Faiblesses constatées :**
1. **Dérive documentaire** : rien n'a été documenté après le 2026-06-18 alors que 4 commits de code ont suivi (marché client, store d'état). Les briefings, la mémoire (`project_state` au 31/05) et les skills sont désynchronisés. La méthode dépend de la resynchronisation manuelle de ~5 sources de vérité — c'est ce qui a cassé.
2. **Coût de cérémonie élevé pour un solo** : ~40 % des commits récents sont `docs:`. Une ÉTAPE client (un bouton) produit 3–4 commits doc. À alléger.
3. **Pas de gate de validation automatique côté Unity** : aucun test client, aucune vérification « clone propre », d'où le problème des `.meta` passé inaperçu 5 mois.
4. **Validation Play manuelle** par le founder (« validé en Play ») : non reproductible par l'agent → c'est précisément ce que le pilotage de l'Éditeur (§5) peut résoudre.
5. **Branche unique longue durée** jamais mergée dans `main` (106 commits).

## 5. Pilotage de l'Éditeur Unity : le plugin suffit-il ? Faut-il le MCP de la capture ?

### 5.1 Deux chemins distincts — ne pas les confondre

| | **A. AI Assistant + « Unity MCP » (ta capture)** | **B. Unity CLI + package Pipeline (plugin `unity-cli`)** |
|---|---|---|
| Packages | `com.unity.ai.assistant` (+ generators, inference) — **déjà ajoutés, non commités** | `com.unity.pipeline` (un seul package) |
| Prérequis | Projet lié à Unity Cloud (✅ `cloudProjectId` présent), compte/abonnement ou essai Unity AI, packages **pre-release** | Unity CLI (✅ installé), Unity 6+ (✅) |
| Pont | Édition › Paramètres du projet › IA › Unity MCP → « Bridge » | `unity pipeline install` puis `unity status` |
| Côté Claude Code | Configurer le client MCP indiqué dans la fenêtre Unity MCP | Soit **Bash direct** (`unity command …`), soit `unity mcp configure claude-code` |
| Poids | Lourd (assistant IA intégré, génération d'assets, inférence, ~7 dépendances) | Léger |
| Statut | Preview | Beta (CLI) / experimental (pipeline) |

État actuel vérifié : Éditeur ouvert (PID 10084), **pipeline non installé** (`unity status` → `STATUS_NO_INSTANCES`), **aucun serveur MCP configuré** dans Claude Code.

### 5.2 Réponse à ta question

- **Le plugin seul (skills) ne suffit pas** : sans pont vers l'Éditeur, je n'ai que les fichiers. Je peux écrire C#/UXML/USS (ce qui couvre ~80 % du travail actuel), mais je ne peux pas câbler une scène proprement, assigner un prefab, entrer en Play ni lire la console. Les étapes « wiring manuel Unity requis » et « validé en Play par le founder » de la méthode actuelle viennent de là.
- **Le plugin + le chemin B suffit**, et c'est mon choix recommandé : tout passe par le skill `unity-cli` du plugin déjà installé, un seul package léger, pas d'abonnement IA, et un usage via Bash que je maîtrise sans configuration MCP. Le MCP (`unity mcp configure claude-code`) reste une option si on veut des outils typés.
- **Le chemin A (ta capture) n'est pas nécessaire.** Il ajoute un assistant IA concurrent dans l'Éditeur et trois packages preview. Je recommande de **retirer** `ai.assistant`, `ai.generators` et `ai.inference` du manifest (ils ne sont pas commités, donc retour arrière trivial), sauf si tu veux utiliser l'assistant ou la génération d'assets de Unity pour eux-mêmes.

### 5.2-bis Test réel du 2026-11-01 (chemin B)

`com.unity.pipeline` **0.9.1-exp.1** installé. L'Éditeur expose **166 commandes** (GameObjects, composants, `set_field` pour assigner des références, prefabs, scènes, Play, console, capture Game/Scene view, `script.eval` en C#, tests, build, paramètres, packages).
Vérifié de bout en bout : lecture de la hiérarchie de `Boot.unity` ✅, création puis suppression d'un GameObject ✅, entrée et sortie du mode Play ✅, lecture de la console du jeu en direct ✅, capture du Game view lisible par l'agent ✅.

Incidents rencontrés :
- `com.unity.ai.assistant` 2.21 **embarque déjà** les modules Generators/Toolkit. Ajouter `com.unity.ai.generators` en plus dupliquait toutes les assemblies, et **plus aucun script ne compilait** (ni le jeu, ni le Pipeline), sans que l'Éditeur passe en Safe Mode. `ai.generators` a été retiré du manifest.
- L'AI Assistant renvoie `NoSubscription` : **le chemin A exige un abonnement Unity AI** absent du compte.
- Le serveur Pipeline démarre seulement quand la fenêtre Unity a eu le focus au moins une fois, et il redémarre à chaque recompilation (quelques secondes d'indisponibilité).

### 5.3 Ce que le pilotage débloquerait dans la méthode

- Câblage scène/prefab par l'agent (fin du « wiring manuel requis »).
- Boucle de validation agent : compiler → entrer en Play → lire la console → sortir, à chaque ticket.
- Lancement des tests Unity (EditMode/PlayMode) → introduire enfin des tests client.
- Garde-fou : jamais d'édition YAML de `.unity`/`.prefab` quand un Éditeur est joignable.
- Point d'attention : une erreur de compilation met l'Éditeur en Safe Mode → le pont ne charge plus. Il faut alors corriger le C# hors Éditeur, puis redémarrer Unity.
